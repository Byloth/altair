# Direct3D 9: what the game asks for

Measured on 2026-11-15 with the **recorder** (`crates/runtime/src/d3d9.rs`): an `IDirect3D9` and
a device that accept the calls, keep the minimal state the game reads back, count
everything and draw nothing. A run of 3,000 frames from startup:

```sh
ALTAIR_FRAMES=3000 tools/run.sh      # stops after 3,000 Presents and prints the census
```

In these 3,000 frames the game loads the loading room (`DataPC_LoadingRoom2`) and
the menu world (`DataPC_Map_Menu`), skips the four opening videos (Bink is not there) and stays
in its main loop. What it "shows" cannot be said: there is no image yet. No
key was pressed.

## Device creation

- `Direct3DCreate9(32)`, then `CreateDevice` with a **1280x720 X8R8G8B8** back buffer, no MSAA,
  full screen, automatic depth **D24S8**, behaviour flags `0x42`
  (`HARDWARE_VERTEXPROCESSING | FPU_PRESERVE`… to be verified), immediate interval.
- We declare a GeForce 8800 GTX (vendor `0x10DE`), shader model 3.0, 4 render targets.
- `CheckDeviceFormat` asks for: `R2VB` (ATI trick, refused), `G16R16` and `R16F` as render
  targets, `A16B16G16R16` and `A16B16G16R16F` with filtering, `R32F` with vertex texture query.

## States

- **Render states** set often: 168 `COLORWRITEENABLE` (84,855), 22 `CULLMODE`, 27
  `ALPHABLENDENABLE`, 14 `ZWRITEENABLE`, 24 `ALPHAREF`, 23 `ZFUNC`, 20 `DESTBLEND`, 19
  `SRCBLEND`, 15 `ALPHATESTENABLE`, 25 `ALPHAFUNC`, 52 `STENCILENABLE`, 55–59 stencil. The others
  (about 60) are set once, at the beginning. The full list comes out in the census.
- **Sampler states**: U and V addressing (1, 2), W (3), magnification, minification and
  mip filters (5, 6, 7); rarely LOD bias, max mip, anisotropy.
- **Vertex declarations** (18): position as `FLOAT3`, `FLOAT4`, `SHORT4`, `SHORT4N`
  (types 2, 3, 7, 10); weight as `UBYTE4N`; blend indices as `UBYTE4`; normal and tangent
  as `FLOAT3` or `UBYTE4`; texture coordinates as `FLOAT2`, `FLOAT3`, `D3DCOLOR`, `UBYTE4`,
  `SHORT2N`; colour as `D3DCOLOR` (usage 10, type 4).

## Behaviours to remember for the renderer

- **`DrawPrimitiveUP` is the most frequent draw** (41%): vertices passed on the fly, typical of
  interface and post-processing.
- **Occlusion queries are created at every use**: 20,328 `CreateQuery`, that is almost 7 per
  frame, each used once and released. Likewise the vertex buffers: 6,242 created, two per
  frame. The real renderer must recycle these objects.
- `TestCooperativeLevel` and `GetAdapterCount` are called twice per frame;
  `GetAdapterMonitor` once.
- The game asks for the address `127.0.0.1` (telemetry or development tools): network absent.

## GPU in WSL

Verified on 2026-11-15 with `target/release/altair-gpu-probe` (crate `crates/gpu-probe`, which
lists the adapters seen by wgpu 24).

| wgpu backend | Adapter | Type |
|---|---|---|
| Vulkan | llvmpipe (Mesa 25.2.8, LLVM 20) | **CPU**: software rendering |
| OpenGL, default | llvmpipe | **CPU** |
| OpenGL with `GALLIUM_DRIVER=d3d12` | **D3D12 (NVIDIA GeForce RTX 4070 Ti)**, OpenGL 4.6 | GPU |

- There is nothing to install: Mesa 25.2.8 is already present (it came with other dependencies) and
  contains the `d3d12` driver, which runs OpenGL on top of Direct3D 12 through `/dev/dxg`.
  It has to be selected with `GALLIUM_DRIVER=d3d12` and `LD_LIBRARY_PATH=/usr/lib/wsl/lib`.
- **There is no Vulkan on the GPU**: Ubuntu does not ship the `dzn` driver (Vulkan on D3D12);
  the only Vulkan available is software.
- With the OpenGL backend wgpu offers BC compression (the game's DXTs) and 8 render targets;
  it does not offer filterable 32-bit float textures.
- WSLg is active (`DISPLAY=:0`, `WAYLAND_DISPLAY=wayland-0`): a window opened from WSL appears
  on the Windows desktop. There is also the audio server (`PULSE_SERVER`).

Tests made with the same program:

- `altair-gpu-probe triangle build/triangle-gpu.png`: a triangle drawn off screen
  on the RTX 4070 Ti, read back and saved as PNG. The image is correct (triangle with the three
  blended colours on a dark background, 52,416 pixels covered); identical in the count to the one
  produced in software.
- `altair-gpu-probe window 4`: a real window through winit and WSLg, 640x360
  `Rgba8UnormSrgb` surface, **212 frames presented in 4 seconds** on the GPU. Whether the window
  appeared on the desktop only the user can confirm.
- When the window is closed the process ends with a memory error (core dump) after
  finishing its work: it is in the destruction of window and graphics context, to be fixed
  when there is the real renderer.

Off-screen rendering with readback is also the way the
game's frames will be checkable without looking at the screen.

Consequence: in WSL the renderer can be developed on the real GPU by going through OpenGL. The
"wgpu → direct DX12" path exists only when compiling for Windows.

### Shader translator (`crates/shader`, `altair-shaderc`)

D3D9 shader model 3.0 bytecode → WGSL. 1,488 distinct shaders extracted from the game
(`ALTAIR_DUMP_SHADERS=private/shaders`): 128 vertex and 1,360 pixel. **All of them translate and
pass naga**, wgpu's validator. Validating does not mean being correct: the ones
verified by eye are the 28 used by the two screens.

Instructions the game's shaders use, in order of frequency: `mul mov add mad dp3 cmp
texld nrm dp4 rsq pow rcp lrp max`, then `ifc`/`endif`/`else` (flow control in 410
shaders), `rep`/`endrep` (loops in 255), `slt frc texkill min mova sincos dp2add texldl sge if
log abs exp`. No subroutines, no predicates, no `loop` with `aL`.

Conventions of the WGSL produced (documented at the top of `crates/shader/src/lib.rs`): constants in
one uniform block per stage (256 vectors, 16 integers, the booleans as bits); a fixed
`@location` for every semantic; `vec4f` registers with write masks rendered component by
component; variants for integer attributes (`UBYTE4`, `SHORT4`: they arrive normalized and are
rescaled in the shader) and for the alpha test (which does not exist in wgpu: it becomes a `discard`).

### Renderer (`crates/runtime/src/gfx.rs`)

Off screen: every D3D9 surface is a wgpu texture, and at every `Present` the back buffer
can be saved as PNG.

- **Pipelines** cached by (shader, vertex declaration, target formats, blend
  states, depth, culling, colour mask, topology).
- **Constants**: one large uniform buffer per frame, one slot per draw and per stage,
  bound with dynamic offsets.
- **Textures**: DXT1/3/5 → BC1/2/3; A8R8G8B8 and X8R8G8B8 → BGRA8; A8, L8 and A8L8 expanded to BGRA8
  on load; floating-point targets → RGBA16F; D24S8 → Depth24PlusStencil8.
- **Render pass** opened when first needed and closed when the targets change; `Clear`
  becomes the load operation of the next pass.
- **`DrawPrimitiveUP`** and triangle fans go through a scratch buffer.
- **Half pixel**: the vertex shader shifts the position by half a pixel right and down.
- **`StretchRect`**: a copy with linear filtering over the whole surface.
- A validation error does not stop the game: it is reported and the draw is lost.

### Stencil, scissor, depth bias (2026-11-15)

- **Stencil**: states 52-59 (enable, fail, zfail, pass, function, reference, masks) and
  185-189 (two-sided: in D3D9 the front is clockwise, as in the wgpu pipeline). Reference with
  `set_stencil_reference`; the rest is part of the pipeline key, zeroed when
  stencil is off so as not to multiply pipelines. Only if the depth has stencil.
- **Scissor**: `SetScissorRect` and state 174; the rectangle goes back to the whole target when
  render target 0 changes, like the viewport.
- **Depth bias**: states 195 (constant, float in depth units → multiples of 2⁻²⁴) and 175
  (slope), only for triangles.

### Performance: dynamic buffers, bind groups, constants (2026-11-15)

Measurements with `stats` (control channel) or `ALTAIR_STATS=1`: frames per second, draws, time
in the renderer, submissions to the GPU and bytes of buffer uploaded per frame.

| Scene | Before | After |
|---|---|---|
| Main menu (130 draws) | ~25 fps | 190 fps, 3 ms in the renderer |
| Lab (912 draws) | 22 fps, 37 ms in the renderer | 45 fps, 15 ms in the renderer |
| Animus, DNA helix (1,540 draws) | 2 fps | 27 fps, 25 ms in the renderer |
| Animus corridor with Altaïr (250-310 draws) | (never reached) | 70-90 fps |

Off screen, RTX 4070 Ti through OpenGL on D3D12. In the lab, of the 15 ms in the renderer
10 are the submission (`queue.submit`: wgpu and Mesa executing the 912 draws), the rest is
preparation, half a millisecond per phase. In the DNA helix 20 MB of buffers
uploaded per frame still weigh in ("buffer" phase: 8.5 ms).

What was costly:

1. **One submission for every rewritten buffer.** Rewriting a buffer used by a draw not yet
   submitted would change its data, so everything was submitted first: dozens or hundreds of submissions
   per frame. Now a `Lock` with `NOOVERWRITE` updates in place (it promises not to touch
   data in use), one with `DISCARD` takes a new buffer (the old one stays with the pending
   draws), the others put the new version in the scratch buffer. One submission per frame.
2. **Buffers re-uploaded in full.** Now only the range of the `Lock` is uploaded.
3. **Two new bind groups per draw**, with their views: now they are reused, keyed by (bound
   textures, sampler states).
4. **9 KB of constants per draw**: now they are rewritten only if changed since the last draw.

5. **Thousands of `write_buffer` per frame** (constants and scratch data): now they are
   accumulated in memory and go out in just two writes at submission.

6. **Only what the draw reads is uploaded.** A `Lock` marks the range as "pending";
   the upload happens at the draw, for the intersection with the vertices and indices it uses (for
   indexed draws: `BaseVertexIndex + MinVertexIndex`, `NumVertices`, as the game
   declares them). In the DNA helix: from 20 MB to 0.3 MB per frame, 27 → 28-32 fps. The
   "buffer" phase still costs 6 ms over 1,600 draws: new buffers at every `DISCARD` and many small
   writes.

### The crowd: where the time goes (2026-11-15 afternoon)

Scene of the monks in the tutorial: 3,600 draws. The new "in the shims" counter (time of the rendering
thread inside the runtime, measured with the TSC around every `host_call`) separates
our cost from the game's.

| | fps | frame | in the shims | of which submission | game (the rest) |
|---|---|---|---|---|---|
| Before | 9.1 | 110 ms | 51 ms | 34 ms | 59 ms |
| Image at `-O2` with `Ctx *restrict` | 12.2 | 82 ms | 51 ms | 34 ms | 31 ms |

- **The translated game runs almost twice as fast** with two compilation changes: `-O2` and, above all,
  the context passed as `Ctx *restrict` (`ALTAIR_RESTRICT` in `runtime/altair.h`). Writes
  to guest memory go through a byte pointer, which for C may alias
  everything: without `restrict` the compiler re-reads the guest registers from the context after every
  write. The promise is true (guest memory never contains the context) and the differential
  test stays green. Lab: from 45 to 55 fps.
- **The submission does not go down**: 34 ms for 3,600 draws, 9.4 µs per draw, all inside
  `queue.submit`, that is in the execution of the OpenGL calls by Mesa on top of D3D12.
  Tried with no effect: not repeating identical states between one draw and the next (pipeline, bind
  group, viewport, scissor, buffers: it stays, it is right anyway) and `mesa_glthread=true`.
  It is a limit of the WSL environment, where there is no Vulkan on the GPU (the `dzn` driver is missing):
  on native Windows or Linux wgpu will use D3D12 or Vulkan directly. To be measured again there before
  optimizing further.
- Also removed two string copies and one table lookup for every host call
  (`host_call`): not measurable in this scene, but there were hundreds of thousands per frame.

Remaining lever on the game's side, bigger and longer: keeping the guest registers in local
variables in the generated C (`translator.md`).

### Where the submission time goes, and the submit thread (2026-11-15 evening)

With no `perf` in WSL I wrote a sampling profiler inside the runtime
(`profile.rs`, `ALTAIR_PROFILE=1`, commands `profile reset` and `profile` on the control channel):
a signal a thousand times a second to the rendering thread, which notes where it is executing and, with
a scan of the stack, the first address of our executable that brought it there (to be
resolved with `addr2line -f -C -i -e target/release/altair-run`, adding `0x1000`).

What it showed, in the lab (915 draws):

- with Mesa's driver thread active, half of the rendering thread's time is waiting
  (futex) for that thread; disabling it (`GALLIUM_THREAD=0`) the time shows up where it really is:
  **36% in NVIDIA's D3D12 driver**, 30% in a single page of code;
- **42% of the thread is inside `glDrawElementsInstancedBaseVertexBaseInstance`**: it is the
  draw call itself, where Mesa validates the state and the driver translates it;
- the GPU is at 40% (`nvidia-smi`): the limit is the CPU in the driver, not the card.

Hypotheses tested and discarded, each with a measurement:

| Hypothesis | Test | Outcome |
|---|---|---|
| Too many bytes of constants | upload only the registers the shader reads (`Shader::float_consts`) | no effect on submission; it stays, it costs less |
| The driver waits for the GPU because we rewrite buffers in use | constants and scratch in four rotating copies | from 9.4 to 8.8 ms; it stays |
| Likewise for the dynamic vertex buffers | new buffer instead of writing to a recently used one (`ALTAIR_BUSY=1`) | no effect; off |
| Changing the constants buffer at every draw is costly | experiment with fixed offset (wrong image) | −26% of the submission: it is a part, not the whole |

Conclusion: the cost is per draw inside Mesa and the driver, and from here at most a quarter of it
can be recovered. **The real lever was another one: the game stood still while the driver executed the draws.**

Now the submission happens on a separate thread (`gpu-submit`). The game thread records the commands
(wgpu, with no calls to the driver), collects the frame's writes (constants, scratch,
vertex buffer ranges, textures) and hands everything over as a batch; the submit thread does
the writes, `queue.submit` and the presentation on the window. The queue between the two holds a single
batch: if the submission falls behind, the game waits there.

Two things learned the hard way:

- wgpu, with OpenGL, protects the context with a lock that errors out after one second of
  waiting, and its internal locks do not withstand a resource creation on one thread while
  the other writes to the queue (the game stopped during loading). A **gate** of our own
  (`GATE`) makes the two things mutually exclusive, with no time limit; large writes
  go out in 8 MB pieces so as not to hold it too long.
- Creating buffers every frame (the `DISCARD`s) goes through the gate and waits for the submission in progress:
  discarded buffers now return to a **pool** after four submissions and are reused.

| Scene | Before today | With `-O2` + `restrict` | With the submit thread |
|---|---|---|---|
| Lab (915 draws) | 45 fps | 55-59 fps | **106 fps** |
| Animus, DNA helix (1,900 draws) | 27-30 fps | 30 fps | **64 fps** |
| Tutorial crowd (3,600 draws) | 9 fps | 12 fps | **23 fps** |

After the submit thread I lightened the recording of draws on the game thread (in the
crowd from 17 to 11 ms): if the targets are those of the previous draw the pass is not re-examined,
the pipeline is compared with the last one before looking it up in the table, the constants are written
only once and compared in place. I also put the vertex shader and
pixel shader constants in two separate groups (0 and 3), so that each is rebound only when its own
change: **on the submit thread it had no effect** (38.8 ms before and after), it stays because it is
cleaner.

In the crowd the two threads now weigh almost the same: game 31 ms plus 11 of recording, submission
39 ms. In the lab the limit is the submit thread (9 ms for 915 draws).
`ALTAIR_SUBMIT_THREAD=0` goes back to submitting from the game thread. In a window the presentation
synchronized with the screen happens on the submit thread and no longer stops the game.

Remaining levers: the constants buffer that changes at every draw (up to a quarter of the submission:
constants in a buffer bound only once, indexed per draw), the recording of
draws (17 ms in the crowd), the guest registers in local variables in the generated C.

### Resource recycling (2026-11-15)

The game creates and releases resources continuously (in 12,000 frames: 6,242 vertex buffers,
29,803 queries, 617 textures). Before, nothing was freed. Now a `Release` that reaches zero on
textures, surfaces, buffers and queries puts the resource on hold, and at the end of the frame (`sweep`)
it is freed if the device no longer uses it: Direct3D keeps alive the resources still bound
(textures in the stages, buffers in the streams, render targets), even if the game has released them.
The guest memory, the table entries and the wgpu objects are freed, including the bind groups
that name the texture (otherwise they would be reused for the resource that takes its
address). Implicit back buffer and depth are not freed; the levels of a texture follow
the texture; shaders and declarations stay. The final census prints how many it freed.

### Native Windows: first measurements and striped shadows (2026-11-15)

First run on Windows (user), Vulkan on the RTX 4070 Ti, from the log `run\win\log.txt`:

| Scene | WSL (OpenGL on D3D12) | Windows (Vulkan) |
|---|---|---|
| Submit thread, 915 draws (lab) | 9.0 ms | 0.6 ms |
| Submit thread, 1,650 draws | ~14 ms | 1.5 ms |
| Lab | 106 fps | 130 fps |
| Game scenes with 500-680 draws | — | 170-185 fps |
| Scenes with 2,000-2,200 draws | — | 30-38 fps |

The submission costs ten to twenty times less: WSL's double hop really was the bulk of it. On
Windows the limit is by now the game thread (in the 2,000-draw scenes the submission is under
2 ms and the frame lasts 30).

**Striped shadows on lit surfaces** (reported with two screenshots; visible in
WSL too, I had not noticed): the game keeps the shadow maps in `R32F` targets and we were creating them
as `Rgba16Float`. At 16 bits the depth has 11 bits of mantissa: the comparison with the map goes wrong
in bands. Now `R32F`, `G32R32F` and `A32B32G32R32F` stay at 32 bits when the card declares
`FLOAT32_FILTERABLE` (the log says so: "32-bit float targets"); on those formats
blending is removed, because wgpu does not allow it. In WSL the feature is missing (Mesa's OpenGL on
D3D12) and the targets stay at 16 bits: there the stripes remain, until 32-bit textures
without filtering are handled. **To be looked at again on Windows.**

## Limits of this census

- A single scene, with no input: the real game (city, crowd, shadows), the navigated menus and
  the graphics options are missing.
- The recorder always answers "succeeded": if the game makes decisions from the return
  values (for example from the pixels of the queries, which we always report as visible) the path may
  differ from the real one.
- The declared `caps` are plausible values written by hand, not those of a real card.
